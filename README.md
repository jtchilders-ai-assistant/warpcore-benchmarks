# Warpcore Benchmarks

Benchmark results for LLMs served on **Warpcore** — an NVIDIA DGX Spark (GB10) host at ALCF —
running vLLM. This repo aggregates quality and (planned) throughput benchmarks on a **per-model**
basis, and documents the serving issues encountered on the hardware and how they were fixed.

³ Nemotron-3.5-Lightning's **GPQA-Diamond score is output-budget-sensitive** — it is a deep reasoner whose long chain-of-thought (stripped from `content` by the `nemotron_v3` parser but still counted against `max_tokens`) can exhaust a small budget mid-reasoning, yielding an empty answer scored wrong. Measured curve: **16k → 53.03%** (41% truncated), **32k → 66.16%** (21%), **64k → 76.26%** (only 3% truncated, 97% of items answered — the number shown). The hard-tail items genuinely need p50 ≈ 30k / max ≈ 54k completion tokens. `max_tokens` is a *ceiling not a reservation*: 32–64k is a realistic serving budget for reasoning/agentic workloads (interactive chat would cap 8–16k, trading the hardest ~10–20% for latency). GSM8K (95.07%) and IFEval (86.14% prompt-strict) had negligible truncation. All at greedy `temp=0`, lm-eval 0.4.12. See the [Lightning card](results/nemotron-3.5-lightning-30b/README.md#quality--lm-eval-harness-measured-2026-08-12) for the full budget-vs-capability analysis and the serving recommendation. Peak throughput is still **capped by `--max-num-seqs 128`** (~23× KV headroom), so ~719 tok/s is a floor.

⁴ Qwen3.5-122B-A10B-int4 is **newly brought up** (2026-08-10): serving is verified (smoke test pass) and throughput is measured, but the quality/agentic suites have **not yet been run** on Warpcore. It is the model behind the Reddit "50 tok/s on DGX Spark" report — measured here at **26.9 tok/s single-stream** (matching the ~30 tok/s int4 figure) with a **~228 tok/s aggregate plateau at c≈192**. **MTP/speculative decoding was not enabled**; that is the lever toward the Reddit ~50 tok/s. At INT4 it fits one Spark (62.65 GiB weights + 26.26 GiB KV, 256K context); the FP8 sibling does not. See the [Qwen3.5-122B card](results/qwen3.5-122b-a10b/README.md) for the tokenizer/solo-recipe gotchas and next steps.

⁵ Nemotron-3.5-Lightning **SWE-bench Verified = 51/100 resolved (51%)** on the full n=100 shuffle (11 repos, same seed 42 as the Qwen3.6 run, so the two runs cover the **identical 100 instances** — directly comparable). This **beats the Qwen3.6-35B baseline (44/100)** by +7 and is a strong result for a 30B-A3B model. Scoring is **clean**: 0 harness errors, 98/100 got a fair test verdict, and the only 2 non-submissions are genuine model outcomes (`django-16938` hit the step limit, `django-13033` a real miss) — **not** serving failures. Head-to-head on the shared 100: **33 both-resolved, 18 Nemotron-only, 11 Qwen-only, 38 neither** — Nemotron solves more that Qwen misses than vice-versa. **Getting to this clean number required beating a serving bug:** under sustained long-context load the vLLM/GB10 engine repeatedly *wedged* (`/v1/models` returns 200 but real completions hang/5xx) — reproduced across **three configs on v0.27.1 and again on a v0.27.2rc1 nightly**, confirming a live, unfixed vLLM engine bug on GB10 under long-context MoE generation, independent of the model. An earlier pass scored a floor of 47/100 with 11 instances denied a verdict by the wedge; those 11 were re-run on a fresh endpoint (10 submitted, 1 step-limit), recovering **4 real resolves** → the true **51/100**. Two honest caveats: **(a)** n=100 shuffled is a representative sample (±~5%), not the full 500 → *indicative*, not leaderboard-final; **(b)** the sample is **django-heavy (56/100)**. Per-repo: django 30/56, scikit-learn 4/5, pytest 3/4, sphinx 4/10, matplotlib 2/2, sympy 3/10, astropy 1/5 — the expected difficulty gradient. Also fixed earlier in this run: mini-swe-agent's stock `swebench.yaml` submit step (`cat patch.txt`) intermittently captured raw file-contents instead of a diff → "Patch Apply Failed: only garbage found" false zeros; a robust submit (`git add -A && git diff --cached`) eliminated all patch-apply errors. Model served with the `qwen3_coder` tool-call parser + `nemotron_v3` reasoning parser (both verified working on the nightly), native tool-calling scaffold (`swebench.yaml`), `temp=0`, per-step `timeout=1800`. pi-30 = 29/30 (sole miss P24). Raw at [`raw/swebench/`](results/nemotron-3.5-lightning-30b/raw/) (results + preds JSON). See the [card](results/nemotron-3.5-lightning-30b/README.md#agentic-coding--swe-bench-verified-n100-shuffled) for the full per-repo breakdown, the wedge diagnosis, and the submit-capture fix.

⁶ Ornith-1.0-35B-FP8 **would not start at all** on the GB10 until *two* Marlin switches were set. Its `compressed-tensors` **W8A8 FP8** checkpoint hits a GB10 CUTLASS failure in the **dense/linear** FP8 GEMM (`cutlass_gemm_caller … Error Internal` → EngineCore init fails) that is **separate from** the known MoE-experts CUTLASS crash: `--moe-backend marlin` fixes only the experts, and the model still dies. The full fix is `-e VLLM_TEST_FORCE_FP8_MARLIN=1` (routes `CompressedTensorsW8A8Fp8` to `MarlinFP8ScaledMMLinearKernel`) **plus** `--moe-backend marlin`. Despite the `VLLM_TEST_` prefix this is the production-correct setting on this SM. See [ISSUES.md #13](ISSUES.md). The Marlin FP8 path is a compatibility fallback rather than a fast path, which — together with FP8 weights being 2× the bytes of NVFP4 — is why Ornith's ~464 tok/s peak and 36.95 tok/s single-stream sit below Lightning's despite similar total size. Two more bring-up notes: the `qwen3` reasoning parser returns an **empty `reasoning_content`** (though `content` is correctly CoT-stripped), and the model burns a large thinking budget even on trivial prompts (218 reasoning tokens for a one-word answer), so clients must send a generous `max_tokens` (≥4k chat, 32k+ reasoning/agentic) or answers truncate to empty and silently score wrong.

⁷ Ornith-1.0-35B **SWE-bench Verified = 73/100 resolved (73%)** — the **best agentic-coding result in this repo by a wide margin**, on the same seed-42 n=100 shuffle as the Lightning and Qwen3.6 runs (**identical 100 instances**, directly comparable). That is **+22 over Nemotron-3.5-Lightning (51/100)** and **+29 over Qwen3.6-35B (44/100)**. Head-to-head vs Lightning on the shared 100: **46 both-resolved, 27 Ornith-only, 5 Lightning-only, 22 neither** — Ornith wins the exchange better than 5-to-1, which is a real capability gap, not sampling noise, and is consistent with Ornith being purpose-built by DeepReinforce for agentic coding. The number is **clean**: **0 harness errors**, 91/100 received a fair test verdict, and the 9 non-submissions are genuine agent-budget outcomes (8 `LimitsExceeded`, 1 `ContextWindowExceededError`) rather than serving failures — notably **the vLLM/GB10 long-context wedge that plagued the Lightning run did not recur** on this stack (`0.27.2rc1` aarch64 + Marlin FP8 at `--gpu-memory-utilization 0.55`), and the robust submit step again yielded zero patch-apply errors. Per-repo: django 44/56, sphinx 8/10, sympy 7/10, scikit-learn 4/5, astropy 2/5, pytest 2/4, xarray 2/3, matplotlib/requests/pylint/flask 1 each. Caveats: **(a)** n=100 shuffled is representative (±~5%), not leaderboard-final; **(b)** the sample is **django-heavy (56/100)** and Ornith is especially strong there (79%), so a balanced 500 would likely land lower; **(c)** 8 instances died on the step/cost limit, so 73 is a mild *under*estimate of reach. **Read this alongside the quality columns:** Ornith is *behind* Lightning and Qwen3.6 on GPQA-Diamond (69.70% vs 76.26%/82.32%) yet far *ahead* on SWE-bench — benchmark rank does not transfer across task families. Its pi-30 score (**30/30**, including the token-bucket problem P24 that Lightning failed) points the same way, though pi-30 is now saturated at the top of this model set and no longer discriminates.

⁸ poolside/Laguna-S-2.1-NVFP4 is **newly brought up** (2026-08-22): serving is verified (smoke test, tool calling, and a 60/60 concurrent guided-decoding stress test all pass) and throughput is measured, but the quality and SWE-bench suites have **not yet been run**. Bring-up required **patching vLLM's MoE backend selection** — see [ISSUES.md #14](ISSUES.md). Two things stack: (a) it is a **mixed-quantization** checkpoint (layers 0–39 experts NVFP4, layers 40–47 experts BF16 via `quantization_config.ignore`), so vLLM builds two MoE method objects with **disjoint** legal backends while `--moe-backend` is a single **global** flag — `marlin` is illegal for the unquantized group, `triton` for the NVFP4 group; and (b) the GB10 is **sm_121** while the vLLM aarch64 nightly ships only sm_80/90/100/120 cubins, so letting the oracle auto-select lands on **FlashInfer**, which initialises fine and then dies at the **first decode** with `no kernel image is available for execution on the device` (wrapped misleadingly as `MemoryError` — *not* an OOM). Fix: `--moe-backend marlin` **plus** a `sitecustomize.py` aliasing marlin→TRITON for the unquantized group, gated on capability `(12,1)`. **Sizing:** poolside's own model card says the NVFP4 weights are "roughly 71 GB"; summing the actual safetensors gives **99.7 GB (92.9 GiB)** — ~30% higher, enough to flip a fit verdict. Measured at runtime: 94.48 GiB weights+non-torch leaves only **8.44 GiB KV** (333,604 tokens, 2.55× at 128k). **Throughput:** single-stream is slow at **17.65 tok/s** (~8.5B active params on a bandwidth-bound box, Marlin being a compatibility rather than fast path, and 12 of 48 layers doing global attention); interactive SLO (TPOT<100 ms) holds only to **c=4**. Peak is **~259 tok/s at c≈192, a genuine plateau**: the sweep looked like it was still climbing at c=128 (+40.8%), but c=192 adds only +10.9% and at c=256 the engine admits *fewer* concurrent requests (49 running / 207 queued) — KV-cache pressure, not scheduler headroom, since 94.48 GiB of weights leaves only 8.44 GiB of KV. Latency past c=128 is unusable interactively (mean TTFT 28 s, P99 154 s at c=192). **pi-30 is excluded by design**: it runs its agent processes on Warpcore itself and needs ~40 GiB host headroom, which cannot coexist with 94.5 GiB of resident weights. A first throughput sweep was **discarded as contaminated** (an lm-eval smoke test overlapped it, cf. [ISSUES #6](ISSUES.md)) and is preserved alongside the clean rerun in the card's `raw/`.
⁹ **Scores marked ⁹ are affected by the `message.reasoning` defect — see [ISSUES.md #15](ISSUES.md).** lm-eval reads only `message.content`; when vLLM's reasoning parser fails to initialize its token IDs it can emit `content: null` with the complete answer in `reasoning`, which lm-eval scores as zero. **Laguna GSM8K 96.13% is CORRECTED** — all 186 affected items (14.1%) were re-served and graded with the identical filters; the raw harness output was 83.40%. **Ornith GPQA-Diamond 69.70% is a known UNDERESTIMATE and has not been corrected**: 42/198 items (21.2%) returned empty and scored zero; on served items it is 88.46%, but that figure is an upper bound rather than the answer — on Laguna the recovered items scored 90.3% versus 97.09% for served items, so the defect does not drop questions uniformly at random and exclusion-based estimates are optimistically biased. Ornith and Laguna IFEval figures (5.2% / 5.4% empty) are floors. A re-serve is required before any of these are final.

## What's measured

- **Quality** — [lm-evaluation-harness](https://github.com/EleutherAI/lm-evaluation-harness)
  (GSM8K, IFEval, GPQA-Diamond) run against the live vLLM OpenAI chat endpoint, plus
  [Zapier AutomationBench](https://github.com/zapier/AutomationBench) for agentic business workflows.
- **Throughput** — `vllm bench serve` concurrency sweep (output tok/s, TTFT, ITL/TPOT), climbed until
  throughput plateaus. See each card's Throughput section. (Note: the quality harnesses above record
  no tok/s — throughput is a separate on-box measurement.)
- **Agentic coding** — [pi-30](https://github.com/rick-stevens-ai/pi-30) (30 agentic-coding problems, verifier-graded)
  and [SWE-bench Verified](https://www.swebench.com/) via
  [mini-swe-agent](https://github.com/SWE-agent/mini-swe-agent) (bash-only agent loop; the agent + x86 test
  containers run on a client Mac, the model is served on Warpcore). SWE-bench is reported on a representative
  random 100-instance sample (not the full 500), on a **fixed seed-42 shuffle** so every model here covers the
  **identical 100 instances** and the scores are directly comparable. Ornith-1.0-35B leads at 73/100;
  gpt-oss-120b's SWE-bench run is blocked by a vLLM tool-call serving bug (see its card).

## Reproducing

Each model card lists exact harness versions, endpoints, and flags. The lm-eval pipeline (chat endpoint,
custom clean-extraction tasks, all pitfall fixes) is captured for the maintainer in a Hermes skill
`lm-eval-vllm-endpoint`; the commands are reproduced in each card.
